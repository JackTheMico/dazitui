# 0013. 万象虎词提：确定性优先的最小击数择优

- **状态**: Accepted
- **日期**: 2026-09-18

## 背景与上下文

「词提」= 编码提示（ADR 0008）在对照区逐词展示的待敲编码。ADR 0008 §3 的择优规则只有**击数**一个维度：
`best_code` / `best_composition_code` 按 `(击数, 手区前缀, 码长)` 取最小，**完全不建模「打完这个码能否真的拿到目标词」**。

在万象虎（`tiger.schema.yaml`，`schema/name: 万象虎`，自动判定为 `four_auto_commit` 定长形码）上实测，该规则会产出「看起来最短、实际打不出来或要多按一次键」的提示。

### 实测事实（本机 `~/.local/share/fcitx5/rime`）

1. **dazitui 为万象虎加载的主词典是 `tigress.dict.yaml`**（`char_word/dictionary: tigress` 的 `initial_quality: 9999` 最高，见 `extract_schema_dictionary_candidates`）。它只含单字 + `import_tables` 引来的 `tiger_dicts/tigress/tigress_ci.dict.yaml`。
2. **`tigress_ci`（2.6 MB，`columns: [text, code, weight]`）才是多字词码的实际来源**，收录 138,382 条二字/三字词，全部 4 码，每词仅一条码。例：`结果 igqe 18062`、`情绪 haiq 9993`、`很多人 wlj`、`习惯性 zhhl`。
3. **重码规模**：117,603 个不同码中 17,434 个（14.8%）对应多个词；涉及词条 38,213 个（27.6%）。其中约 15% 的词在其唯一 4 码下**不是首选**（重码组第 2、3 位），必须按数字键选号。例：`jgjr → 个人/佳人/伟人`、`srcl → 发展/发蜡`、`cbku → 不过/不好过`。
4. **4 码捷径只覆盖 tigress_ci 收录的词**。`tiger` 整句通道（`build/tiger.table.txt`）对同一词给的是**逐字全码拼接**（`结果 → ig,d-￣k qe,￣m-0`，即 8 击）；两个通道的码不是一回事。
5. **真 OOV 词（如 `腕间`）在两个通道都不存在**，只能逐字独立上屏。
6. **权重从未被保存**：`word_to_codes: HashMap<String, Vec<String>>`，`add_entry` 只存 code；`get_primary_code` 返回「文件里第一条出现的码」而非权重最高者 → 现状无法判定「首选」。
7. 未收录词走 `best_composition_code` 逐字拼接时，取的是**各字最少击数码**（一简/二简），拼出的串不可照打：如 `的(u) + 人(j) → uj`，既无分隔、也未计空格，实际应为 `u␣ j␣`。
8. `tigress.dict.yaml` 的 frontmatter 带 `encoder` 规则（`length_equal: 2 → AaAbBaBb`、`3 → AaBaCaCb`、`[4,10] → AaBaCaZa`）与第 4 列 `stem`（组词用码，如 `的  10359470  u  un`）。**dazitui 未实现 encoder、未读 stem**；但因 tigress_ci 已显式提供词码，该缺口仅影响未收录词的回退路径。

## 决策

### D1 择优顺序：先过确定性门槛，门槛内取击数最少

不采用加权打分（惩罚系数不直观、调参结果难以解释）。

> **2026-09-18 修订**：初版把「确定性」定为**首选（第 1 位）**，实测把万象虎**全部 3200+ 条简词压掉了**（详见 §修订记录），故把第 2 位（`;` 一键直选）也纳入确定集合，并明确**击数是门槛内的第一排序键**。

### D2 确定性门槛：一次确定按键能取到目标词

- **第 1 位** → 空格；
- **第 2 位** → `;`，**仅当方案把 `;` 绑定为选重键**（万象虎 `key_binder` 明写 `{ when: has_menu, accept: semicolon, send: 2 }`；虎整句 README 同）；
- **第 3 位及以后** → 需要数字键或 `Ctrl+i` 一类组合键，代价更高且未必可用，**不算确定**。

不采用「唯一上屏才算确定」（过严，大量词退化为无解），也不采用「前三位候选内」（过松）。

### D3 词码来源：优先 RIME 编译产物，退回词典 YAML

优先使用 `build/*.table.bin`（及其文本导出 `*.table.txt`）；缺失或解析失败时退回解析 `tigress_ci.dict.yaml` 等纯文本词典。

### D4 取数范围：双通道，按需取词

启动时只读 `tigress` 通道（5.8 MB）建主索引；载文后**只对文中实际出现的词**去 `tiger` 整句通道做一次性反查，得出重码与首选。不整体加载 118 MB 的 `tiger.table.bin`（启动数与内存不可接受）。

### D5 重码非首选词：标位次，击数计入选号键

词提标出选号位次（如 `jgjr·2`），击数计 `4 + 1 = 5`。口径单一、与实际按键一致。

> **影响**：万象虎下击键统计会整体抬高，需同步更新 `dazitui-core/tests/tiger_code_hint.rs` 等既有「4.0 击键门槛」测试基线。

### D6 未收录词：逐字独立上屏 + 显式分隔

每字取「确定且击数最少」的码，逐字之间显式分隔（沿用既有 `␣` 空格标记风格），击数 = `Σ(码长 + 上屏键)`。不采用「逐字全码连打」（8 击，虎码用户实际不这么打），也不保持留空。

## 算法规格

```
候选码集合 C(word) = { tigress_ci 显式码 } ∪ { tigress_simp_ci 简词码 } ∪ { OOV: 逐字独立码序列 }
过滤   : 仅保留「一次确定按键可取到目标词」的码   # D2：第 1 位(空格) 或 第 2 位(`;`，需方案绑定)
排序键 : (击数, 位次, 码长)                       # 击数含上屏键/选号键，见 D5/D6
若门槛后 C 为空: 取击数最少的码，并标出选号位次
```

### D2' 权重相同时的位次：按码表录入顺序，不按词条字符串

`code_index` 里同一码的多个词条按**权重降序**排；权重相同（虎整句 `.codes.txt` 无权重列，故全部相同）时依赖**稳定排序保持录入顺序**。

曾因额外加了 `then_with(a.word.cmp(&b.word))` 二次排序，把「的」判成第 2 位（按码点 工 U+5DE5 < 的 U+7684，「工作」反被排到「的」前面），提示成 `u;`；实际「的」是首选，应为 `u␣`。码表的录入顺序本身即作者声明的优先级（单字一简在前、简词在后），不可被字典序覆盖。

`CodeHint` 需扩展字段以承载位次标注（`rank`）与逐字分隔形态；`strokes` 语义由「码元数」升级为「真实按键数」。

## 实现落地（2026-09-18）

`dazitui-core/src/scheme.rs`：

- 新增 `code_index: HashMap<String, Vec<IndexedEntry>>`（编码 → 共享该码的词条 + 权重），
  由 `add_entry_weighted` 在解析时登记；`parse` 按词典声明的 `weight` 列（缺省按 Rime 默认第 3 列）取权重。
  **`weight` 此前从未被保存**，`get_primary_code` 返回的其实是「文件里第一条」，故本项是全部优化的前置。
- `eval_candidate` / `best_four_code`：按上式评估与择优；`four_code_len` 只数实际会按下的字符。
- `build_hint_for_word_four`：定长形码专用分支。整词命中走择优；未命中则逐字独立上屏，
  各字码以 `␣`（U+2423）显式分隔。
- `mark_commit_key`：需补上屏键时在提示串尾追加 `␣`；选号位次不在码串里，交给渲染层。
- `primary_or_best`：让 `resolve_strokes_and_keys`（击键统计）与词提共用同一择优，口径单一。
- `CodeHint` 新增 `rank: u8`（1 = 首选）；`code_hint.rs::hint_display_text` 在 `rank >= 2` 时追加 `·n`。

### 性能：只为该用的方案建索引

反查索引使 kongmingma（273 万词条）加载从 1.47s 涨到 2.22s（+51%），而它是并击方案、根本用不到索引。
故新增 `collect_index` 开关：`.schema.yaml` 分支先算 `four_auto_commit` 再载词典；
`.dict.yaml` 分支预读同名 schema（仅解析 YAML）预判；预判失误时由 `ensure_code_index` 补一次带索引的重读。
改造后 kongmingma 回到 1.33s，万象虎（23.8 万词条）356ms 保持不变。

## 待确认（实现后的结论）

1. **table.bin 解析未实现**：`tigress_ci.dict.yaml` 与 `tigress.table.bin` 同源、仅 2.6 MB 且含码与权重，
   已能完成首选/重码判定；OOV 按 D6 走逐字独立上屏只需单字码（来自 `tigress.dict.yaml` 主表）。
   故 D3 实际只落地了「退回词典 YAML」这一支，二进制解析的收益不成立、未做。
2. **用户词典调频未纳入**：`tigress.userdb` 会改变实际首选顺序，dazitui 读不到。
   当前以静态词库权重为准 —— 打熟的高频词实际可能比提示的位次更靠前（偏保守，不会误导到打不出）。
3. `·n` 与既有 `␣` 标记风格并存：`␣` 表示要按的键，`·n` 表示选号位次，二者语义不同、可同时出现。
   （ADR 0014 起选号位次已改为直接写出真实按键 `;` / `'` / 数字，`·n` 仅存于本 ADR 的早期描述。）

## 修订记录（2026-09-18，用户报障）

### 修订 1：一码简词被全码压掉（万象虎「不是」应为 `c;`，实际给 `cbot`）

**现象**：`不是` 提示 `cbot`（4 击），用户预期 `c;`（2 击）。

**根因**：`tigress.dict.yaml` 的 `import_tables` 还引了 `tiger_dicts/tigress/tigress_simp_ci.dict.yaml`
（3224 条简词：1 码 26 / 2 码 63 / 3 码 3115，权重一律 5000）。`不是` 因此有两个候选：

| 候选 | 来源 | 位次 | 击数 |
|---|---|---|---|
| `c` | tigress_simp_ci 简词 | 2（前面是不的一简 `c`，权重 3217018） | 2 |
| `cbot` | tigress_ci 全码 | 1（唯一） | 4 |

初版 `best_four_code` 把「`rank == 1`」当硬门槛，`c` 直接被过滤，**3200+ 条简词无一生效**。

**修正**：确定性集合放宽到 `rank == 1 || (rank == 2 && 方案绑定了 ';' 选重)`，且**击数为第一排序键**。
实测 2 万词样本：位次分布 `{1: 19122, 2: 829, 3: 43, 4: 4, 5: 2}`；第 3 位及以后仅 49 例，
且经核对全是「该词只有这一个码」的情形（与修订前一致，未引入新回归）。

回归测试：`tests/tiger_code_hint.rs::test_wanxiang_one_key_jian_ci_beats_full_code`。

### 修订 2：权重相同的位次按字典序排，把「的」误判为第 2 位（虎整句）

**现象**：虎整句 `的` 提示 `u;`（第 2 位），实际应为 `u` + 空格（首选）。

**根因**：`code_rank` 在权重相同时用 `then_with(a.word.cmp(&b.word))` 二次排序。
`tiger_sentence.codes.txt` 无权重列（整表权重 0），`u` 组含 `的`（第 6 行）与 `工作`（第 2545 行），
按码点 工 U+5DE5 < 的 U+7684 →「工作」被排到首位。

**修正**：去掉字典序二次排序，依赖 `sort_by` 的稳定性保持**码表录入顺序**
（单字一简在前、简词在后，正是作者的优先级声明）。用户报障本身即佐证：单字「的」确实先于简词「工作」。

连带修正（原断言建立在错误位次上）：虎整句 `工作` `u␣` → `u;`；`东西` `r␣` → `r'`；
`自己` `o'`(第3) → `o;`(第2)，`知道` 才是 `o'`(第3)。已用独立脚本按「录入顺序」复算全部 102 个多字词，与实现输出零差异。

回归测试：`tests/tiger_code_hint.rs::test_tiger_sentence_single_char_yijian_is_first`。
