# ADR 0018: 空明码词提架构——一击优先、分色对齐与选重位次

## 状态
已接受 (Accepted) — 2026-09-27

## 背景与问题 (Context)
在空明码（并击方案）打词与跟打练习中，原词提（`CodeHint`）存在以下三项体验与度量缺陷：
1. **一击字感知缺失**：许多高频双字词（如「好人」）并非词库一击词（需 4 字母 2 击），但其组成字符均为 204 个极速一击字。原词提直接显示不易辨识的 4 字母双手并击码（如 `hr` 对应的复杂并击），而空明码选手在肌肉记忆上更倾向于先后击出两个熟悉的单字一击并击。
2. **左右手手区无视觉分色**：空明码一击字赛文中，左手字与右手字分别使用粉色与黄色高亮，选手能凭借色块瞬时反应手区。但在词组或常规赛文中，词提仅能整体展示单一颜色（双手并击青色或默认色），无法分色指示各字的左右手归属。
3. **重码与非首选位次隐形**：原 ADR 0013 为优化 270 万大词库载入性能，对并击方案清空了候选位次索引（`code_index`）。这导致当某个词并非首选候选时（如 2 选），词提无法知晓其 `rank`，既不提示选重键，也不在击数统计中计入选重击键，造成练习提示与真实输入割裂。

## 决策 (Decision)

### D1 · 优先级梯队：一击词绝对优先
- **第一梯队（一击词）**：若目标词在空明码中是一击词（1 击单并击，如「中国」`Uz`、「可以」`k'`），最高优先保留一击词提示，绝不拆解为 2 击的一击字。
- **第二梯队（一击字转译）**：若该词不是一击词，但其所有字符全部收录于 204 个一击字表中（`KONGMING_1HIT_CHORDS`）：
  - 仅当 `一击字总击数 <= 词库整词码击数` 时进行转译（双字词 2 击 = 2 击触发转译；四字成语词库 2 击 < 逐字 4 击则保护不转译）。
  - 转译后以空格分隔各字编码（如 `h r`、含空格并击字如 `h␣ r`）。
- **第三梯队（词库整词编码）**：保留词库最优整词码。若该词不是首选候选，按 D3 规则追加选重键。
- **第四梯队（逐字全码回退）**：未收录词回退到逐字全码。

### D2 · 左右手独立分色与排版对齐
- `HintCell` 升级为分段渲染模型：词格内部的每个单字按自身手区（`HintHand::Left` / `HintHand::Right`）独立着色（左手粉色、右手黄色）。
- 词格两端用于居中对齐的补白空格及单字间的间隔空格不施加手区颜色（`HintHand::None`）。
- 词格列宽与换行打包锁步机制保持不变（`max(词宽, 码宽)`）。

### D3 · 候选位次显示与真实物理击数度量
- 空明码等纯并击方案保留候选反查索引（`code_index`），准确定位目标词在重码组内的位次（`rank`）。
- **按键直传式选重**：若目标词不在首选（`rank > 1`），在编码尾部直接追加数字键（如 2 选追加 `2`，形成 `oc2`、`bGCw2`）。
- **击数精确度量**：非首选词追加选重键后，总击数计为 `基础并击数 + 1`，忠实反映选手的物理敲击次数，彻底杜绝码长与击键（KPS）失真。

## 后果 (Consequences)
- **正面**：
  - 空明码选手在常规长文与词组练习中能清晰感知一击字的连打路径，手感大幅提升。
  - 左右手分色直观强化左右手交替打字的视觉反馈。
  - 非首选词带有明确的选重位次指示，击数度量与实际按键 100% 吻合。
- **代价与权衡**：
  - 空明码方案载入时保留 `code_index` 会占用约数百兆内存，但载入由后台异步线程完成，不会阻塞 TUI 主渲染循环。

## 补充（2026-11-08）：以当前 XSIME 方案为准的准确性修正

现实运行环境从 `fcitx5-rime` 迁移到 XSIME 后，词提的数据源与可行性判据需要随实际部署方案修正：

- **数据源优先 XSIME 激活方案包**：方案发现顺序改为
  `$RIMES_USER_DIR/schemes/packages/<active>/`（或 `$XDG_DATA_HOME/rimes/...`）→ 其余方案包 → 旧 `fcitx5-rime` 目录；
  同名方案以先出现者为准，避免继续提示旧部署词库中已修正/易主的编码。
  固定码表（`KONGMING_1HIT_CHORDS` / `KONGMING_1HIT_WORDS`）只作兜底：一击词表条目必须经词库确认该码确属此词，
  防止过时条目把重码提示给别的词（例如旧表「看到 ;K」已被「之后 ;K」取代）。
- **一击字来源扩展**：仍以 204 静态表为主（记法简洁且已与 kongmingmas 一致），表外字符若词库确有一击码也参与转译；
  `f=` / `=d` / `a_=` / `=_a` 这类并击逻辑码在提示中还原为实际按键 `f` / `d` / `a␣`。
- **逐字转译计入选重键**：比较时使用「各字击数（含各自选重键）之和」，不再以字符数粗估。
- **选重位次的物理上限**：并击采集器的字母表会占用数字键（空明码为 `7/8/9/0`），这些数字不能用于选重；
  最大可选位次由 `chord_composer/alphabet` 推导（空明码为 6）。超过上限的重码视为不可选，跳过并改用次优可行码。
- **码尾数字不是选重键**：空明码码元本身可含 `7/8/9/0`，`S7`、`Y0` 等仍计 1 击；选重键由 `rank` 显式计入，不再解析码尾数字。
- **主词优先（两字以上词）**：空明码以打词为主，词库有可用整词码时直接展示整词码，不再因「逐字一击字总击数持平」而降级为空格分隔的逐字词提
  （如「好人」显示 `H,rF` 而非 `h r`）；单字仍优先展示一击指法。整词码内部按
  「总击数 → 基础并击数（简码优先）→ 选重位次 → 码面长度」择优，能用简码就用简码。
  逐字一击字词提仅在词库未收录整词码时作为回退。

## 补充（2026-11-14）：一击字词提二次修订——撤销「主词优先」

实践反馈（空明码含一击字的词语「没有任何的提示」）表明，2026-11-08 的「主词优先」补充与一击字练习场景冲突：
练习者更关注逐字一击并击路径，而整词码（如 `7B2`/`@k*=`/`y'`/`,G`）视觉上难以解码，被当作「没有提示」。

- **撤销 2026-11-08「主词优先」对一击字词提的限制**：凡完全由一击字（204 静态表或词库 1 击码）组成的词（含多字词），
  一律显示空格分隔的逐字一击码，词库整词码让位（如「好人」→ `h r`、「不同」→ `b T`、「就可以」→ `j k i`）。
- **一击词仍绝对优先**（决策 D1 第一梯队不变）：词库确认为 1 击多字并击词的（如「中国」`Uz`、`可以` `k'`），保留一击词提示，绝不拆解为逐字一击字。
- **含非一击字的词**仍走整词码（决策 D1 第三梯队），不受本次修订影响。
- **单字**仍优先展示一击指法（如「中」→ `f`）。

实现位置：`SchemeDict::build_hint_for_word_pure_chord` 的 T2 入口由
`if chars.len() == 1 || best_word.is_none()` 放宽为「全部字符均有一击指法即转译」，
并移除与整词码击数比较的 `char_strokes <= word_strokes` 门控（见 `dazitui-core/src/scheme.rs`）。

## 补充（2026-11-15）：一击字词提三次修订——改为「按键最少」

2026-11-14 的「全逐字一击」在实践中产生新矛盾：用户希望含一击字的词语优先**打词**而非打单。
典型如「没有把握」`mYBW`、「耐心等待」`NxdD`、「新手」`xySu`（两字皆带空格一击字）等多字词，
整词码击数（2 击）并不多于逐字一击（4 击），却因上一版规则被强制拆成逐字一击码，偏离了
空明码「多字词优先打词」的肌肉记忆。

- **总原则：按键最少**。对由一击字组成的词，比较「逐字一击总击数」与「词库整词码击数」：
  - 逐字一击击数**严格少于**整词码击数时，才回退为空格分隔的逐字一击码；
  - 否则（整词码更省或**持平**）一律优先展示整词码。持平即打词，符合「两字以上优先打词」的诉求。
- **一击词仍绝对优先**（决策 D1 第一梯队不变）：词库确认为 1 击多字并击词的（如「中国」`Uz`），保留一击词提示，绝不拆解。
- **含非一击字的词**走整词码（决策 D1 第三梯队），不受本修订影响。
- **单字**恒展示干净的一击指法（如「中」→ `f`，避免 `f=` 这类并击逻辑码），始终走逐字分支。

实现位置：`build_hint_for_word_pure_chord` 的 T2 入口门控改为
`let use_per_char = chars.len() == 1 || char_strokes < word_strokes;`
（`word_strokes` 取自 `best_word` 整词码击数，缺省 `u32::MAX`）。
仅当单字、或逐字一击严格更省时采用逐字码；其余情况穿透到 T3 整词码（见 `dazitui-core/src/scheme.rs`）。

## 补充（2026-11-17）：一击字词提四次修订——子词动态规划切分

三次修订仍有一个结构性缺口：词提单元来自 jieba 分词、内置词边界或短语合并，**单元边界未必等于最优打字边界**。
旧逻辑只在「整词码」与「逐字一击」两者间二选一，一旦单元横跨两个语素就退化：

- 「注意力是」：整词未收录 → 走逐字一击 `ZC y␣ L s`（4 击），而 `注意力`(ZCyl) + `是` 只需 **3 击**；
- 「没有任何的」：整词未收录 → 逐字一击 `M i r␣ iE d`（5 击），而 `没有任何`(`*'`) + `的` 只需 **2 击**。

- **决策：单元内做子词动态规划**。`dp[i]` = 从第 i 个字到词尾的最少总击数，段候选三类：
  1. 词库整词码（含一击词；非首选追加选重数字并 +1 击，受并击字母表选重上限约束）；
  2. 静态一击词表兜底（仅多字段；且该码必须经词库确认确属此词，防过时条目串码）；
  3. 单字一击指法（204 静态表为主，表外用词库 1 击码补齐）。
- **代价与择优**：段代价 = 该段击数；总代价 = 各段之和。同分时优先「段数更少、靠前段更长」，
  即**先整词、再长词、末单字**——这正好复刻「持平优先打词」的肌肉记忆。
- **段间记法**：各段码以**单空格**分隔（如 `ZCyl s`、`*' d`），与逐字一击词提 `h r` 的既有记法一致；
  空格只是视觉分隔，**不计入击数**（击数取 DP 总代价）。
- **兜底不变**：若存在字符既无整词码覆盖、又无一击指法（生僻字、ASCII 混排），仍回退逐字全码拼接，避免半截提示。

本次修订**统合了前三版规则**，不再需要「一击词优先」「主词优先」「逐字严格更省才拆」这三个特判：
- 一击词（1 击）在 DP 中必然最优，等价于「一击词绝对优先」；
- 整词码不劣于逐字时因「同分少段」胜出，等价于「持平优先整词」；
- 逐字一击严格更省时自然胜出，等价于「严格更省才拆」。

## 补充（2026-11-17）：`_` 是码元，提示区不得剥除

**现象**：词提里「同事」只显示 `E`，而它的空明码码串是 `_E`——提示缺键，照码打字必错。

**根因**：`code_hint::strip_hand_prefix` 把编码前导 `_` / `+` / `-` 一律当「手区修饰符」剥掉。
这条约定来自 yoyo-pure：那边的 `_d` 是 algebra `xform|^(单手键序列)$|_$1|` 派生出的单手输入形式，
且方案自己用 `prompt_format: xform/[-=_+]//g` 主动抹掉——确实不是按键。
但空明码的 `_` 是 chord algebra **直接产出**的码元：

- `xform/(w-d-f-|j-k-o-)/_/`（左手 `wdf` / 右手 `jko` 并击）
- `xform/(90-)/_/`（数字键 `9+0` 并击）

词库中 68 条编码以 `_` 开头（`同事 = _E`、`或是 = _!`、`就在 = _.` 等），被剥除即等于丢掉一击。

**决策**：

1. 新增 `HandPrefixStyle { Modifier, Literal }`，由 `SchemeDict::hand_prefix_style()` 按 `pure_chord`
   判定（纯并击 = `Literal`，其余 = `Modifier`）。`Literal` 下前导 `_` / `+` / `-` 原样显示并计入列宽；
   `%`（空格并击标记）始终剥除（它本就是渲染层标记）。
2. 列宽与提示文本必须共用同一 `style`：字面 `_` 占一列，修饰符 `_` 不占列，否则提示行与正文行错位。
3. 配色不据前缀推断手区：`_` 同时代表左手 `wdf` 与右手 `jko`，无法判手，故 `Literal` 下统一按双手并击上色
   （`hand_of_code_with`），与 `ZCyl` 等多码元提示一致。
4. 兼容：`layout_code_hint_line` / `layout_code_hint_grid` / `hint_cell_widths` 默认仍走 `Modifier`，
   yoyo-pure 的 `_d` → `d`、`+e` → `e` 不变；内置空明一击字赛文用 `_` / `+` 前缀编码手区，同样走默认 `Modifier`。

非内置长文与内置词组/单字赛文的提示行、宽度计算、8×4 点阵单字提示均已接入该判定。

回归保护：`code_hint::tests::layout_literal_hand_prefix_keeps_underscore_symbol`、
`scheme::tests::hand_prefix_style_follows_pure_chord`。

**遗留**：物理键展开（`decompose_code` 系列）仍按前导 `_` 判定为单手前缀；空明码走 chord algebra
分支展开，目前未暴露问题，待后续与提示区口径一并核对。

## 补充（2026-11-20）：内置一击字/词数据同步到方案当前词库

**背景**：dazitui 内置的一击字赛文（204 字）与一击词赛文（618 词）生成于 2026-09，
而空明码方案在 2026-11-15/17 完成「简码体系全量收敛 / 一词一码 / 码位回补」，
词条的当前码面与词频归属已变：原 204 字中 201 字的码面改变、3 字不再是一击；
原 618 词中 259 词不再满足一击，另有 86 个常用词成为一击词。

**决策**：内置数据与静态提示表改为从方案当前词库重算，口径与方案 `tools/km_chord_model.py` 一致：

- **一击字**：前 1500 常用单字中「一击上屏」（一次并击可达、唯一候选且无延伸）的字，
  按词频排序，共 **455** 字。单手码沿用简洁记法（`f=` → `f`、`a_=` → `a␣`），
  双手码保留方案逻辑码（如 `ID`）；手区由一次并击的左右手按键反推。
- **一击词**：dazitui 自有 1500 常用词表中，存在「一次并击可达且该词为词库首候选」的码的词，
  按词频排序，共 **765** 词（445 一击上屏 + 320 一击后按空格）。同等条件下优先无需空格的自动上屏码。
- 静态表 `KONGMING_1HIT_CHORDS` / `KONGMING_1HIT_WORDS` 与内置赛文数据同源生成，
  `table_chord_logical_code` 对双手一击码直接采用表中逻辑码。
- 内置一击字赛文的提示区：左/右手区仍用 `_`/`+` 前缀着色，双手一击码不再添加 `-` 前缀，
  直接以双手并击青色显示（此前的 `-` 分支保持不可达）。

**理由**：练习内容必须与输入法实际可打出的码一致；旧的「码长恰为 2」判据既漏掉 `=`/`_` 类码元，
也会把已改派给其它词的旧码当成当前一击词，导致练了打不出来的码。
